[2025-02-21 09:30] Gavin Tuck (Firmware Lead):
Dr Haddad, Gavin Tuck, firmware. You are right that it isn't, and you've
essentially diagnosed it for us.

We have reproduced this internally this morning. Firmware 4.2.1 changed how
the HL7 timestamp is assembled - it now derives the time from a counter seeded
at boot rather than reading the real-time clock directly. The counter runs
slightly fast, and on the Pro it runs quite a lot fast because the retic and
flagging code extends the cycle it counts. So the error grows with uptime and
resets when you power cycle.

The instrument display, the printed report and the audit log all read the
clock directly, which is why they're right. That asymmetry is the reason you
found this and we didn't.

Affected fields are OBR-7, OBX-14, OBR-22 and MSH-7. Result values are not
affected - this is a timestamp defect only. No number you have reported is
wrong.

What happens next:
- Investigation opened as VBI-0091.
- A corrected firmware is in progress. I'm not going to give you a date I'm
  not sure of; I'd expect weeks, not months.
- Interim mitigation: power cycle at the start of each working day. That holds
  the error to a few minutes.
- If you'd prefer, we can roll both instruments back to 4.2.0, which does not
  have this defect. That loses you the RFID read reliability fix in 4.2.1,
  which from your ticket history is not something you've been affected by.

--- Resolution ---
Root cause: VeriScan firmware 4.2.1 HL7 timestamp accumulator defect
(VBI-0091). Result values unaffected.
Actions: instruments rolled back to 4.2.0 (FSV-2025-0171), then updated to
4.2.3; VBB-0041 issued; drift reconstruction supplied for historical data.
This ticket and VBST-3910 were the two reports that triggered VBI-0091.
